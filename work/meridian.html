From a map to a data product

Where was a ship last observed, what changed since the previous report, and how much can we safely conclude? Meridian turns those questions into an interactive globe, a persistent observation pipeline, and a transparent scenario workspace.

This is a separate project from my Global Crisis Simulator. Its focus is the practical work of building a reliable data product: validating timestamps, joining vessel identity to position reports, preserving history, and communicating missing coverage.

The engineering

Cached map layers and lightweight geometry during dragging reduce repeated coastline projection work. The web application uses TypeScript and Cloudflare D1 to store received observations, study-area transitions and voyage watches. A Python service provides PostgreSQL/PostGIS storage and an optional continuously running AISStream collector through Docker.

  • Async ingestion: concurrent HTTP requests, WebSocket reception, bounded queues, connection pooling and reconnect backoff.
  • Data structures: MMSI-keyed hash joins, bounded metadata caches, spatial grid lookup and composite keys for idempotent observations.
  • Quality controls: event-time validation, duplicate filtering, impossible-speed quarantine and preservation of unknown values.
  • Algorithms: geodesic distance, dwell-state detection, deterministic Monte Carlo simulation and a separate illustrative NetworkX routing module.
  • Delivery: schema migrations, cross-language model parity tests, a CI definition, architecture decisions and reproducible scenario exports.

Tracking a voyage

The globe catalogs all 28 major passage references in IMF PortWatch, including Hormuz, Malacca, Suez, Panama and Bab el-Mandeb. Observed cargo ships and tankers entering a passage study area are enrolled in an onward watch.

Arrival goals can be selected from 2,065 ports. A ship’s flag country does not establish where it is going. The system therefore uses an explicit destination goal, treats missing reception as a gap, and labels sustained low-speed activity near the destination as an arrival candidate requiring confirmation.

Detailed coastline clipping keeps vessel symbols off dry land without moving the underlying reported coordinates. Timestamped movement trails are drawn only across short, observed intervals.

Better inputs, clearer estimates

Marine context comes from the DWD wave model through Open-Meteo, with forecast-valid time and grid resolution shown explicitly. A cost worksheet separates owner operating exposure from charterer time exposure, adds user-entered fuel and other costs, and allocates a share to the modeled shipment.

Optional benchmarks link to Costamare and Scorpio Tankers’ Q2 2026 reports. These historical fleet averages are not live quotes for the selected ship. Weather conditions are not converted into invented disruption probabilities.

Evidence and limits

The connected default feed provides actual Finnish/Baltic AIS observations. The Railway deployment has a configured AISStream collector; no exhaustive global coverage is claimed.

Passage study areas are approximate. The system cannot establish a physical canal transit from sparse observations, and map geography may omit narrow waterways. Cost scenarios use stated cargo and disruption assumptions: AIS does not reveal a manifest, and the model is not a calibrated disruption or retail-price forecast.

SQL marts and DAX definitions are included for analytics work. Snowflake integration, learned forecasting and validated voyage mining are future milestones. Railway hosts the API and WebGL frontend; source and build history are available on GitHub.

Why I built it

Meridian brings together the skills I want to develop in data engineering and analysis: reliable ingestion, clear data contracts, geospatial reasoning, durable storage, reproducible models, and honest communication of uncertainty.
